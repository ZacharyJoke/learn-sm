# 05 · 编码、字节序与随机数规范

> 一句话价值：统一「内部只传 byte[]、边界才做 Hex/Base64」的纪律，并让密钥/IV/nonce 都来自配置正确的 SecureRandom，消灭最常见的互操作与启动阻塞事故。

---

## 🧭 核心概念

- 密码算法处理的数据本体永远是 **字节数组 `byte[]`**。Hex、Base64 只是字节的**文本表示（representation）**，不是数据本身；在「需要文本」的系统边界（JSON、URL、日志、配置项）才编码，进入业务/密码运算前一律还原为 `byte[]`。
- **字符集是字符串与字节的映射表**：同一字符串用 UTF-8 和 GBK 得到不同字节，摘要/签名随之不同。所有边界转换显式指定 `StandardCharsets.UTF_8`，不依赖系统默认值。
- **字节序（Endianness）**：多字节整数在字节流中的排列顺序。密码标准与网络协议默认**大端（Big-Endian，高位在前）**；Java 的 `DataOutput`、`ByteBuffer` 默认也是大端。
- **随机数是密码安全的地基**：密钥、IV、nonce、盐都必须来自密码学安全随机数生成器（CSPRNG），`java.util.Random`、时间戳、自增序号都不合格。

### 贯穿本篇的场景

一个报文要经过**小程序 → Java 服务 → Go 网关**三处：前端习惯 Hex，Java 服务 JSON 里用 Base64，Go 侧长度字段按大端解析；上线后还出现过容器启动时所有请求卡在获取随机数、以及 GCM nonce 由时间戳生成差点引发复用。团队需要把编码与随机数规范一次定死。

## 🧾 编码方式对比与选择

| 编码 | 膨胀率 | 字符集 | 典型场景 | 注意点 |
|---|---|---|---|---|
| **Hex** | 2.0× | `0-9a-f`（约定小写） | 标准向量、测试断言、短指纹、日志核对 | 大小写统一；肉眼可逐字节核对 |
| **Base64** | ≈1.33× | `A-Za-z0-9+/` 与 `=` | JSON/HTTP 传输二进制、证书/SPKI/PKCS8 | 标准 MIME 每 76 字符可换行，传输建议不换行 |
| **Base64URL** | ≈1.33× | `A-Za-z0-9-_`，通常去 `=` | URL 路径、查询参数、JWT | 用 `withoutPadding()`，避免 `+` 被变空格、`/` 破坏路径 |
| 直接字符串化 | —— | —— | ❌ 永远不要 `new String(密文)` | 非文本字节经字符集映射后不可逆损坏 |

选择口诀：**对人核对用 Hex；JSON/证书用 Base64；进 URL 用 Base64URL。**

## 🛠 工程方法与 API

### 1）统一 Codec（JDK 17+，无需额外依赖）

```java
import java.nio.charset.StandardCharsets;
import java.util.Base64;
import java.util.HexFormat;

public final class GmCodecs {

    private static final HexFormat HEX = HexFormat.of();                 // 小写
    private static final HexFormat HEX_UPPER = HexFormat.of().withUpperCase();

    private GmCodecs() {
    }

    // ---------- Hex ----------
    public static String toHex(byte[] bytes) {
        return HEX.formatHex(bytes);
    }

    public static byte[] fromHex(String hex) {
        return HEX.parseHex(hex); // 非法字符直接抛异常，不静默截断
    }

    // ---------- Base64 ----------
    public static String toBase64(byte[] bytes) {
        return Base64.getEncoder().encodeToString(bytes);
    }

    public static byte[] fromBase64(String b64) {
        return Base64.getDecoder().decode(b64);
    }

    // ---------- Base64URL（无填充） ----------
    public static String toBase64Url(byte[] bytes) {
        return Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);
    }

    public static byte[] fromBase64Url(String b64url) {
        return Base64.getUrlDecoder().decode(b64url); // 解码器对有无填充都兼容
    }

    // ---------- 文本边界 ----------
    public static byte[] utf8(String text) {
        return text.getBytes(StandardCharsets.UTF_8);
    }

    public static String utf8(byte[] bytes) {
        return new String(bytes, StandardCharsets.UTF_8);
    }
}
```

> JDK 8/11 没有 `HexFormat`，可用 BC 的 `org.bouncycastle.util.encoders.Hex`（`Hex.toHexString` / `Hex.decode`）；接口层方法不变，便于升级 JDK。

### 2）字节序与长度前缀

```java
import java.nio.ByteBuffer;

public final class WireNumbers {

    private WireNumbers() {
    }

    /** 大端 2 字节无符号长度前缀 + 内容（对接 Go 侧 binary.BigEndian）。 */
    public static byte[] lengthPrefixed(byte[] data) {
        if (data.length > 0xFFFF) {
            throw new IllegalArgumentException("长度超过 2 字节前缀范围");
        }
        ByteBuffer bb = ByteBuffer.allocate(2 + data.length); // 默认 BIG_ENDIAN
        bb.putShort((short) data.length);
        bb.put(data);
        return bb.array();
    }

    public static byte[] readPayload(ByteBuffer bb) {
        int len = Short.toUnsignedInt(bb.getShort());
        byte[] data = new byte[len];
        bb.get(data);
        return data;
    }
}
```

要点：

- 不要依赖 `byte` 直接表示 0–255——Java 的 `byte` 是**有符号 -128–127**，做数值运算前要 `b & 0xFF`；
- 看到 `ByteBuffer.order(ByteOrder.LITTLE_ENDIAN)` 或 `DataInputStream` 与自定义结构体混用要警惕，跨语言先对一个整数报文验证；
- 文件头、版本号、长度字段在协议文档中显式标注「大端/小端、位还是字节」。

### 3）SM2 C1 的 `04` 非压缩前缀

SM2 密文 C1 是曲线上的临时公钥点，标准编码是 **`0x04 ‖ x(32B) ‖ y(32B)`，共 65 字节**：

- `04` 表示**非压缩点格式**（另有 `02/03` 压缩格式，国密实践中不常用）；
- 部分系统（尤其前端 sm-crypto 的部分模式、C 库配置）收发的是**不带 04 的裸 x‖y（64 字节）**，对接时必须在适配层显式补/去前缀，不能两边默认；
- 判断规则只看协议约定，不靠猜长度。

## 🎲 SecureRandom：选型、配置与排障

### API 参数表

| 写法 | Linux 典型实现 | 用途与风险 |
|---|---|---|
| `SecureRandom.getInstanceStrong()` | `NativePRNGBlocking`（读 `/dev/random`） | 符合「强随机」语义，**可能阻塞**；适合低频生成根密钥 |
| `new SecureRandom()` | `NativePRNG`（取数走 `/dev/urandom`） | 业务 IV/nonce/DEK 的常规选择，现代系统不阻塞 |
| `SecureRandom.getInstance("NativePRNG")` | 显式指定 | 容器中想绕开阻塞配置时用 |
| `SecureRandom.getInstance("SHA1PRNG")` | JDK 软件实现 | 平台无关兜底；不要先 `setSeed` 当密钥派生技巧用 |

### 1）业务侧统一工厂

```java
import java.security.NoSuchAlgorithmException;
import java.security.SecureRandom;

public final class Randoms {

    private Randoms() {
    }

    /** 业务高频使用（IV/nonce/DEK）：urandom 语义，线程安全，全应用共享一个实例。 */
    public static SecureRandom forBusiness() {
        return Holder.BUSINESS;
    }

    /** 低频根密钥：如需「强」随机可用，但要接受潜在阻塞，切勿放请求热路径。 */
    public static SecureRandom strong() {
        try {
            return SecureRandom.getInstanceStrong();
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException("无强随机数实现", e);
        }
    }

    public static byte[] bytes(int len) {
        byte[] b = new byte[len];
        forBusiness().nextBytes(b);
        return b;
    }

    private static final class Holder {
        private static final SecureRandom BUSINESS = new SecureRandom();
    }
}
```

`SecureRandom` 本身**线程安全**，可全局单例；`Cipher`/`Signature` 才需要每次新建。

### 2）容器启动/请求阻塞排障

现象：服务启动或首个请求长时间卡住，`jstack` 显示线程阻塞在 `NativePRNGBlocking`、`Java_javaSecuritySeed...` 或读取 `egd` 的 native 调用。

根因与机制：

- 老版本配置/老内核上，`getInstanceStrong()` 与种子收集读取 **`/dev/random`**，而 `/dev/random` 在估计熵不足时**阻塞**；虚拟机/容器常因 I/O 事件少、熵池低而中招；
- `/dev/urandom` 在密码学意义上同样安全（输出不会因为「估计熵」归零而停），现代内核（约 4.8 起）`getrandom()` 在初始化完成后不阻塞。

配置与处置（参数表）：

| 手段 | 做法 | 适用 |
|---|---|---|
| 指定熵源 | JVM 参数 `-Djava.security.egd=file:/dev/urandom`，或改 `java.security` 中 `securerandom.source=file:/dev/urandom` | 容器/虚拟机通用首选 |
| 换用 API | 热路径用 `new SecureRandom()`，不用 `getInstanceStrong()` | 立即解阻塞 |
| 提升系统熵 | 宿主机装 `haveged`（老内核）、挂载硬件 RNG（`rngd`/virtio-rng） | 无法改 JVM 参数时 |
| 升级基础镜像 | 较新内核的 Docker 基础镜像 + JDK 17（走 `getrandom`） | 根治 |
| 现场确认 | `cat /proc/sys/kernel/random/entropy_avail`；`jstack` 找 Blocking PRNG | 排障取证 |

> 注意：`securerandom.source` 主要影响种子/Blocking 实现；无论怎么配置，都**不要**为了「复现」给生产随机源喂固定种子。

### 3）随机数误用案例

| 误用 | 后果 | 正解 |
|---|---|---|
| `new Random()` 生成密钥/IV | 状态可预测，密钥等于公开 | `SecureRandom` |
| nonce = `System.currentTimeMillis()` | 同毫秒、多实例即碰撞；可预测 | 12B 随机或计数器（第 4 篇） |
| `new SecureRandom(固定byte[])` / `setSeed(固定)` | 输出完全确定，形同明文 | 不播种，让系统自种子 |
| 每个加密对象 new 一个 SecureRandom | 未必不安全，但反复自种子可能加剧熵消耗/性能差 | 全局共享一个 SecureRandom |
| 用 UUID v4 当 GCM nonce | 长度/布局不稳定，且仍受随机 nonce 次数上界约束 | 12B 专用随机或计数器 |

## ❓ 常见问题

**Q1：Hex 和 Base64 会降低安全性吗？**
不会，它们是无损表示；风险在于编解码不一致或把字符串当字节再处理。

**Q2：Base64 标准解码报非法字符？**
多为混入空格换行（用 `getMimeDecoder`）或拿到的是 URL 安全字符（用 `getUrlDecoder`）；先判断来源再选解码器。

**Q3：为什么前端发的 C1 我这边解析失败？**
看是否带 `04`、Hex 大小写、是否 64/65 字节；这是 SM2 互通第一高发点。

**Q4：单元测试想要固定 nonce，算「固定种子」吗？**
测试向量测试可以显式传固定 nonce（确定性验证）；但生产代码路径不能内置固定值，固定值只存在于测试代码中。

## ✅ 最佳实践 / ❌ 反模式

- ✅ 内部方法签名一律 `byte[]`，编解码集中在边界层与统一 `GmCodecs`
- ✅ 所有字符串/字节转换显式 UTF_8；整数统一大端
- ✅ 业务随机数全局共享一个 `SecureRandom`；容器显式配置 urandom
- ✅ 对接协议书面写清：C1 是否带 `04`、Hex 大小写、Base64 是否填充
- ❌ `new String(任意密码学字节)`、无字符集 `getBytes()`
- ❌ 热路径使用会阻塞的强随机、或用时间戳当 nonce
- ❌ 给生产 CSPRNG 设置固定种子
- ❌ 把 Base64 当加密：它没有密钥，谁都能解码

---

## 🚫 什么时候不要这样做

- **不要在 URL 里用标准 Base64 明文**：`+`/`/`/`=` 会被改写，用 Base64URL。
- **不要把「需要压缩」作为选编码的理由去压缩密文**：密文是随机字节，压缩无效还可能泄露长度信息。
- **不要为了跨平台「绝对一致」用软件 SHA1PRNG 并自管种子**：正确做法是统一调用 `SecureRandom`，让各平台使用各自受认可的熵源。
- **不要在业务代码里到处散落编解码逻辑**：一处实现、全项目复用（第 7 篇包结构）。

---

## 🕳 常见坑点

1. **`HexFormat.parseHex` 遇到奇数长度/非 Hex 字符直接抛异常**：上游先做 trim、统一小写与去 `0x` 前缀。
2. **有符号 byte**：日志把 0xFF 打成 -1 引起误判；核对以 Hex 为准。
3. **默认字符集随镜像变**：`file.encoding` 在不同容器不同，显式 charset 才能跨环境一致。
4. **阻塞随机伪装成「服务启动慢」**：上线前在容器里实际抓一次线程栈，别只在开发机验证。
5. **随机 nonce 的次数上界被忽视**：单密钥加密量级规划（第 4、6 篇）要与随机数方案一起设计。
