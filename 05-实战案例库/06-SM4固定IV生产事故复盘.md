# 案例六：SM4 固定 IV 生产事故复盘（支付批次报文重复出款事件）

> 类型：故障复盘｜难度：⭐⭐⭐⭐｜七段式：🎯 背景 → 🚨 现象 → 🔍 排查 → 🧐 根因 → ✅ 解决 → 📈 效果 → 📝 总结
>
> 声明：本案例为**虚构教学案例**，机构名称、金额、人员均不对应任何真实机构；目的是建立「确定性加密 + 缺失防重放」复合故障的排查直觉。

---

## 🎯 案例背景

**业务**：虚构「汇收宝」聚合支付平台，为中小商户提供批量代付能力（工资代发、保险理赔款、供应商结算）。平台每日按商户生成支付批次报文文件，经专线投递至清算渠道，由渠道侧校验后代为出款。

**数据量（故障前基线）**：

- 日均批次文件约 1.1 万个，涉及金额约 4.6 亿元；单文件 2 KB～2 MB（数十至数千笔明细）。
- 工作日 3 个固定批次时点：09:00、13:30、17:00；峰值约 80 文件/秒。

**架构（与本事件相关部分）**：

```mermaid
flowchart LR
  subgraph pay_zone ["支付平台"]
    BIZ["代付业务系统"]
    GEN["批次文件生成器"]
    CRYPTO["加密组件(事发版本)<br>SM4-CBC + IV 全零(缺陷)"]
    LOCAL[("密文落地目录")]
  end
  subgraph channel ["清算渠道(合作方)"]
    RCV["接收与解密"]
    CHECK["格式/总额校验<br>(无批次号幂等: 缺陷)"]
    PAY["出款执行"]
  end
  BIZ --> GEN --> CRYPTO --> LOCAL --> RCV --> CHECK --> PAY
```

**密码设计（事发时）**：

- 报文加密：SM4-CBC（GB/T 32907），DEK 每周轮换、由配置文件明文注入（**违反密钥零硬编码原则**）。
- IV：代码中 `new IvParameterSpec(new byte[16])`，即**全零固定 IV**。
- 文件无数字签名、无消息级防重放；依赖通道专线与文件落地目录权限做防护。

**SLA 承诺**：批次文件接收成功率 99.9%；重复出款类资损事故等级为 P0，要求 30 分钟内响应、2 小时内止血。

---

## 🚨 问题现象

### 时间线（以 2026 年某工作日为基准，虚构）

| 时刻 | 事件 |
|------|------|
| D-9 上午 | 清算渠道侧「文件格式校验失败」告警较基线增多（事后判断为攻击者试拼接密文块） |
| D 08:57 | 平台正常生成并投递 09:00 批次，约 4200 个文件 |
| D 09:02-09:40 | 渠道侧陆续完成解密、校验与出款 |
| D 10:31 | 渠道对账系统提示：**3 个批次号与历史批次重复**，但仍完成出款，涉及 126 笔、合计 **38.6 万元（虚构）** |
| D 10:38 | 平台值班接到渠道电话通报，触发 P0 响应 |
| D 10:52 | 平台侧暂停批量代付通道、通知渠道拦截未出款批次（大部分资金尚未出款或在途） |
| D 11:40 | 确认重复出款明细，启动与渠道的联合追回；15:20 前 38.6 万元全部冻结/追回，无实际资损 |
| D 14:00 | 安全团队在密文落地服务器发现异常登录（一个运维账号于 D-10 凌晨有陌生城市登录记录，疑似钓鱼失陷） |
| D+1 | 密文样本比对，发现确定性前缀规律 |
| D+2 | 代码审计定位全零 IV，根因确认 |

**现象的三个层次**：

1. **业务层**：批次号重复却出款——渠道无幂等控制。
2. **数据层**：不同文件密文开头若干块高度雷同——确定性加密。
3. **入侵层**：失陷账号具备密文落地目录读取权限，且 D-9 有大量文件读取行为。

---

## 🔍 排查过程

### 第一步：对账异常定性（D 10:31-11:10）

渠道对账文件显示，3 个重复批次号分别对应 11 天、13 天、17 天前已成功执行的历史文件；文件大小、明细笔数与历史文件**完全一致**，初步定性为**历史文件重放**，而非平台重复生成。核查平台生成器日志：对应批次号当日无生成记录——文件不是从业务系统正常链路产出的，判断为有人向渠道投递目录重新推送了历史密文文件。

### 监控指标对比表（事发窗口 vs 前 14 天基线）

| 指标 | 基线（前14天同时段均值） | 事发窗口 | 判断 |
|------|------------------------|---------|------|
| 批次文件接收量 | 约 4200/批次 | 4203（多 3 个） | 增量小，流量监控几乎不可见 |
| 批次号重复数 | 0 | 3 | 强异常信号，但渠道侧当时无对应告警规则 |
| 文件格式校验失败 | 0～2/日 | D-9 单日 17 次 | 事后串联：拼接尝试的痕迹 |
| 密文目录读取（运维账号） | 日常 ≤ 30 次/日 | D-9 达 940 次 | 异常数据访问 |
| 解密失败率 | 0.02% | 0.02%（重放文件本身可正常解密） | 重放不触发任何密码错误，传统监控盲区 |

**中间结论 1**：单纯监控「加解密失败率」发现不了重放——合法密文重放依然能正确解密。必须以业务幂等（批次号）+ 访问行为审计来发现。

### 第二步：密文样本比对（D+1）

安全人员从历史目录取同一商户连续 20 个工作日的工资代发批次密文，逐块（16 字节）比对，发现：

- 第 1 块（报文头：版本/报文类型/商户号）**20 个文件完全相同**；
- 第 2～4 块中，固定格式段对应的密文块大量雷同；仅金额、账号所在块不同；
- 同一文件复制后重新投递，密文与原文件**逐字节一致**。

验证性计算（受控测试环境，仅用于验证算法实现与现象）：

- SM4/ECB 标准向量：密钥与单块明文均为 `0123456789abcdeffedcba987654321`，密文 `681edf34d206965e86b3e94f536e4246`，确认密码库 SM4 实现正确——问题不在库，在使用方式。
- 复现实验：同一明文、同一密钥、IV=全零 加密两次，密文完全一致；改明文最后一块，前面密文块不变——与样本现象吻合，确认 **IV 固定导致 CBC 确定性输出**。
- 拼接实验：取文件 A 的头部块 + 文件 B 的明细块拼接，由于 CBC 中 `P(n)=D(C(n)) XOR C(n-1)`，被拼接位置相邻的第一个明文块出现乱码（对应 D-9 的 17 次格式失败），但后续块可正常还原——说明攻击者能在「损坏一块」的代价下重组报文结构。

### 第三步：代码审计定位（D+2）

审计加密组件提交历史与代码，定位到：

```java
// 事发代码（脱敏后的问题形态，非真实代码）
public byte[] encrypt(byte[] plaintext) {
    Cipher cipher = Cipher.getInstance("SM4/CBC/PKCS5Padding");
    SecretKey key = new SecretKeySpec(dekFromConfig(), "SM4");
    cipher.init(Cipher.ENCRYPT_MODE, key,
            new IvParameterSpec(new byte[16])); // 全零固定 IV
    return cipher.doFinal(plaintext);
}
```

并发现：`dekFromConfig()` 直接读取 yml 中明文密钥；渠道接口协议中未规定签名与防重放字段。**中间结论 2：密码缺陷（固定 IV）+ 协议缺陷（无签名/无幂等）+ 账号失陷三者叠加，才构成了实际事故。**

## 🧐 根因分析

### 技术根因

1. **CBC 模式固定 IV（全零）**：CBC 下 `C(1)=E(P(1) XOR IV)`，IV 固定则相同前缀明文必然产生相同前缀密文，泄露报文结构；且固定 IV 为跨文件密文块拼接提供了可预测的链接关系。
2. **无完整性与来源认证**：文件没有 SM3withSM2 签名，渠道无法判断文件是否由合法平台、在合法时间生成，历史文件原样重放即被接受。
3. **渠道侧缺少批次号幂等控制**：重复批次号仅靠人工对账发现，未在受理时拦截。

### 过程根因

- 加密组件由普通业务开发按「对称加密=选个模式+16 字节 IV，填 0 即可」的错误经验编写；团队内无密码评审清单。
- DEK 明文写在配置文件中，违反密钥零硬编码；密文落地目录对运维账号开放读取，最小权限缺失。
- 红蓝对抗与密评未覆盖该条链路（被当作「内网专线通道」而排除在评估范围外）。
- 已有代码扫描规则中没有「固定 IV / CBC / 密钥硬编码」检测项，缺陷无任何自动化防线。

### 为什么传统监控全部失效

重放文件是**合法密钥、合法密文、可正常解密**的文件：解密成功率、CPU、延迟一切正常。能发现它的只有三类信号：业务幂等键冲突、安全访问行为异常、密码学新鲜性（签名/时间戳/nonce）缺失。事故前三类信号均未建设。

## ✅ 解决方案

### 紧急止血（D 当天至 D+3）

1. **通道熔断**：暂停批量代付通道，与渠道建立人工复核白名单，逐批次放行；30 分钟内完成，符合 P0 响应要求。
2. **业务侧先补幂等**：渠道受理时以「机构号+批次号」做唯一约束，重复批次直接拒收——在密码修复上线前先堵住重放路径。
3. **加密算法紧急切换 SM4-GCM**：当天热修，DEK 不变但 nonce 改为每次加密由 `SecureRandom` 生成 12 字节随机值并随文件头传输；GCM Tag 同时提供完整性，任何篡改/拼接立即解密失败。
4. **文件签名与防重放**：文件头增加 `fileId`、`timestamp`、`nonce`，全文件（含文件头）做 SM3withSM2 签名；私钥临时由密码机托管，渠道侧验签并校验时间窗口（±10 分钟）与 nonce 去重。
5. **历史数据处置**：盘点近 6 个月历史批次文件，在受控解密区逐批用新方案重加密（双人操作、全程审计、明文不落盘）；确认失陷账号可读取范围，轮换该范围全部密钥；渠道侧历史批次加入幂等库防止遗留重放。
6. **账号与溯源**：封禁失陷账号、强制全员改密并补钓鱼演练；保留取证镜像配合内部调查。

### 长效修复（D+5 至 D+45）

- **KMS 化**：DEK 改为一文件一密，由 KMS 注入（应用只见密钥句柄/解密授权）；废除配置文件中的密钥字段，配置扫描加入门禁。
- **密码组件统一封装**：集团级 `CryptoService` 固化选型——SM4 默认 GCM 随机 nonce、SM2 固定 sm2p256v1/ID `1234567812345678`/C1C3C2（GM/T 0009）；禁止业务代码自行调用 `Cipher.getInstance` 拼接模式串。
- **静态扫描门禁**：上线固定 IV、`/CBC/`、`/ECB/`、密钥硬编码、验签返回值未判断等规则（参见案例 05），合并请求强制扫描。
- **协议升级**：与渠道更新接口协议，把签名、时间戳、nonce、幂等批次号写入规范，双方各有验签与去重实现，并做互通测试。
- **密评扩围**：将所有「专线+文件」类链路纳入年度密评；建立密码评审 checklist 与开发培训。

## 📝 经验总结

### 可迁移结论（附适用边界）

- **对称加密禁止固定 IV/nonce**：CBC 固定 IV 泄露前缀信息；GCM 同密钥下 nonce 复用可直接破坏安全性。边界：任何以「确定性加密」为前提的特殊设计都必须经密码专项评审。
- **加密不解决重放**：机密性、完整性、新鲜性是三类独立目标，必须分别由加密、签名/MAC、时间戳+nonce+幂等键保障。
- **监控要覆盖业务幂等与访问行为**：纯密码成功率指标对重放攻击天然失明。
- **专线/内网不等于可信**：内部账号失陷后，内网链路面对的是主动攻击者。
- **密码缺陷需要工程化防线**：统一密码组件 + 静态扫描门禁 + 密评，三层都不能省。
