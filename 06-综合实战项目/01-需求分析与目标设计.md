# 01 · 需求分析与目标设计

> 项目：`gm-crypto-suite`（SM2/SM3/SM4 国密能力组件工程）
> 坐标：`com.gmcrypto:gm-crypto-suite:1.0.0`；JDK 17 基线（JDK 21 实测）；Spring Boot 3.4.6；BouncyCastle `bcprov-jdk18on:1.84`
> 本篇定位：在写第一行业务代码前，把「为什么做、做什么、不做什么、如何验收」讲清楚，作为后续设计与验收的唯一基准。

---

## 1. 愿景与背景

### 1.1 背景

国内企业级系统在身份鉴别、数据传输、存储加密、电子签章等场景中，合规要求普遍指向 GM/T 系列国密算法（SM2 数字签名、SM3 密码杂凑、SM4 分组密码）。团队在落地时反复遇到同一类问题：

- 各业务线各自封装，参数选择不一致（ECB、全零 IV、`new Random()`、硬编码密钥等反模式层出不穷）；
- 密码学 API 使用门槛高，SM2 的用户 ID（userId）、密文拼接顺序（C1C3C2）、签名初始化顺序等细节容易出错，且错了往往要到联调或审计阶段才暴露；
- 缺少一个「安全默认、可运行、可测试、可审计」的参照工程，新人入职与新业务接入成本高。

### 1.2 愿景

构建一个基于 Spring Boot 3 + BouncyCastle 的国密能力组件工程 `gm-crypto-suite`，作为团队未来 `crypto-common` 基础库 / SDK 的种子工程：

- **开箱即用**：以工具类与 Spring Bean 两种形态提供 SM2/SM3/SM4 能力；
- **安全默认**：默认 GCM、每次随机 IV/nonce、强随机源、密钥零硬编码；
- **测试完备**：标准算法向量守门，23 个 JUnit 5 用例全绿方可发布；
- **可审计**：内置静态审计器，把常见密码学反模式拦截在编码阶段。

### 1.3 工程目标（一句话）

用一个单模块、可启动、接口可调用、测试可复现的工程，完整演示「SM2 + SM3 + SM4 数字信封」与「HTTP 接口签名验签（防重放）」两条企业级主线。

## 3. 功能需求（FR）

编号规则：`FR-NN`，优先级 P0（必须）/ P1（应有）。

| 编号 | 优先级 | 功能需求 | 关键验收点 |
|------|--------|----------|------------|
| FR-01 | P0 | 编码工具：十六进制（Hex）、Base64、UTF-8 双向转换 | 与 JDK `HexFormat`/`Base64` 行为一致，往返不失真 |
| FR-02 | P0 | 强随机工具：基于 `SecureRandom.getInstanceStrong()` 生成随机字节 | IV/nonce/密钥均可由其生成，不可退化为 `new Random()` |
| FR-03 | P0 | SM3 摘要：字节数组摘要、`InputStream` 流式摘要 | 空串与 `"abc"` 标准向量断言通过 |
| FR-04 | P0 | HMAC-SM3：密钥化消息认证码 | 不同密钥产出不同结果 |
| FR-05 | P0 | SM4 密钥生成：128 位（16 字节）密钥 | `KeyGenerator` 产出，长度恒定 16 字节 |
| FR-06 | P0 | SM4-GCM 加解密：12 字节随机 nonce、128 位 tag、支持 AAD | 往返一致；篡改密文必然失败 |
| FR-07 | P1 | SM4-CBC 加解密：随机 16 字节 IV、PKCS5Padding | 往返一致；IV 每次随机 |
| FR-08 | P0 | SM2 密钥对生成：`sm2p256v1` 曲线 | 公钥/私钥可用于签名与加解密 |
| FR-09 | P0 | SM2 签名 / 验签：`SM3withSM2`，支持 userId（默认 `1234567812345678`） | 正常验签通过；篡改报文、userId 不一致均失败 |
| FR-10 | P0 | SM2 加解密：C1C3C2 密文格式 | 往返一致（BouncyCastle 默认输出） |
| FR-11 | P0 | SM2 DER / PEM 读写：X509/PKCS8 DER 与 PEM 互转 | PEM 写出后可重新加载并完成签名验签 |
| FR-12 | P0 | 数字信封封包 `seal`：随机 DEK + SM4-GCM（AAD 绑定收件人 keyId）+ SM2 加密 DEK + SM3 摘要 | 产出结构完整的 `EnvelopeData` |
| FR-13 | P0 | 数字信封拆包 `open`：解 DEK → GCM 解密校验 → SM3 摘要复核 | 往返一致；篡改密文/密钥/摘要分别被拒绝 |
| FR-14 | P0 | 密钥版本管理：注册、查询、列举、状态流转（ACTIVE/ROTATED/REVOKED） | 状态变更可查；不存在密钥报 `KEY_NOT_FOUND` |
| FR-15 | P0 | HTTP 签名验签：校验 `X-App-Id`/`X-Timestamp`/`X-Nonce`/`X-Signature` 四头 | 合法请求放行；缺头/过期/错签分别拒绝 |
| FR-16 | P0 | 防重放：时间戳窗口 + nonce 一次性判定 | 同一 nonce 第二次请求返回 409 |
| FR-17 | P0 | 请求体缓存：Filter 缓存 body，供拦截器摘要与 Controller 复用读取 | 拦截器读后 Controller 仍能拿到 body |
| FR-18 | P1 | 静态密码审计：5 条规则（ECB / 弱随机 / 硬编码 Hex / 内嵌私钥 / 全零 IV） | 对样例代码可稳定命中规则并给出文件与行号 |
| FR-19 | P1 | 审计命令行入口：通过 `--audit=<path>` 在启动时扫描 | 无参数时不影响正常启动；有参数输出告警日志 |
| FR-20 | P1 | 演示接口：`/api/signed/echo`（签名保护）、`/api/demo/envelope`（信封演示） | 接口可调通并返回预期字段 |

## 4. 非功能需求（NFR）

### 4.1 性能

| 编号 | 指标 | 目标 |
|------|------|------|
| NFR-P-01 | SM3 摘要 | 单报文摘要为微秒级；流式摘要支持常量内存（8 KB 缓冲） |
| NFR-P-02 | SM4 处理 | 具备吞吐 / 延迟基准数据（JMH 占位，上线前补齐实测值） |
| NFR-P-03 | SM2 使用 | 单次 HTTP 签名请求验签不超过一次 SM2 运算；信封中 SM2 仅加密 16 字节 DEK，不用于长报文 |
| NFR-P-04 | 内存占用 | 流式处理不随报文体积线性膨胀；请求体缓存上限可治理 |

### 4.2 安全

- 密钥零硬编码：源码、配置、日志中均不得出现真实对称密钥或私钥；
- 对称加密默认使用 GCM（认证加密），IV/nonce 每次由强随机源生成，禁止全零/固定 IV；
- 信封 AAD 绑定收件人 `recipientKeyId`，防止密文被搬运到其他密钥上下文重放；
- 时间戳窗口（默认 ±300 秒）+ nonce 一次性判定，共同防御重放攻击；
- 异常响应与日志不回显密钥、明文与底层堆栈细节。

### 4.3 兼容性

- 编译目标与基线：JDK 17（`maven.compiler.release=17`），在 JDK 21 实测通过；
- 框架：Spring Boot 3.4.6，Servlet API 使用 Jakarta 命名空间（`jakarta.*`）；
- 密码库：统一锁定 `org.bouncycastle:bcprov-jdk18on:1.84`，全工程不允许出现第二套 BC 版本；
- SM2 密文与标准体系一致采用 C1C3C2 顺序（BouncyCastle 默认）。

### 4.4 可观测性

- 关键密码操作具备可追踪的日志埋点（算法、操作、结果、keyId/指纹），且默认脱敏；
- 静态审计结果带规则号、严重级别、文件与行号，可直接进入工单系统；
- 为运行时指标预留命名规划（操作计数、延迟、验签失败、重放拦截、审计命中），本期以日志形态落地。

### 4.5 可测试性与可维护性

- 标准算法向量（SM3 空串 / `abc`、SM4-ECB 单块向量）必须作为自动化断言；
- 工具类无状态、Spring Bean 依赖清晰，单元测试可不启动容器完成；
- 包结构按能力域划分，单模块即可表达全部层次，便于后续抽取为公共库。

## 5. 范围与不做的事

### 5.1 本期范围（In Scope）

- SM3（含流式、HMAC-SM3）、SM4（GCM + AAD、CBC）、SM2（签名验签、加解密、DER/PEM）；
- SM2 + SM3 + SM4 数字信封的封包 / 拆包与 JSON 结构；
- 密钥版本存储（本地内存实现）与 HTTP 接口签名验签（防重放）；
- 静态密码审计器与命令行入口；演示接口；23 个自动化测试。

### 5.2 本期不做（Out of Scope）

- 不接入真实 KMS / HSM：私钥由进程内存持有，仅定义 `KeyVersionStore` 抽象；
- 不做密钥持久化：`gm.keys.dir` 仅为预留配置，本地存储为内存版，重启后密钥重建；
- 不做注解式签名开关、不提供统一门面 `CryptoFacade`（保持按能力域直连）；
- 不实现 SM4-CTR、SM4-ECB 的业务封装（ECB 仅用于标准向量验证，并被审计规则视为反模式）；
- 不做分布式 nonce（本期单机内存）、多收件人信封、密钥自动轮换编排；
- 不提供多模块 Maven 布局、不发布制品到私服。

## 6. 风险初表

| 编号 | 风险描述 | 可能性 | 影响 | 应对策略 |
|------|----------|--------|------|----------|
| R-01 | BouncyCastle 版本与 JDK 不匹配或多版本共存 | 中 | 高 | 锁定 `bcprov-jdk18on:1.84`，单模块依赖收敛，CI 依赖树检查 |
| R-02 | SM2 签名参数错误（userId 设置时机/顺序）导致互通失败 | 中 | 高 | `setParameter` 先于 `initSign/initVerify`；用例固化默认 userId 与错配场景 |
| R-03 | 误用 ECB / 固定 IV / 弱随机等反模式 | 中 | 高 | 安全默认 API + 静态审计规则 + 代码评审清单 |
| R-04 | 日志或异常泄露密钥、明文 | 中 | 高 | 统一脱敏规范，异常响应仅返回错误码，评审与测试双重检查 |
| R-05 | nonce 被恶意灌爆或先于验签写入造成污染 | 中 | 中 | 先验签、后登记 nonce；TTL 过期清理；规划分布式存储 |
| R-06 | 内存密钥重启丢失，历史信封无法打开 | 高（演示环境） | 中 | 文档明示限制；生产路线指向 KMS/HSM；信封结构与存储解耦 |
| R-07 | 性能未经验证、SM2 被滥用于长报文 | 低 | 中 | JMH 基准占位 + 架构约束（SM2 只包 DEK） |
| R-08 | JDK 基线漂移（本地高版本 API 误入） | 低 | 中 | `release=17` 编译约束，CI 使用 JDK 17 构建 |

## 7. 验收总目标

| 维度 | 验收标准 |
|------|----------|
| 功能完整 | FR-01 ~ FR-20 全部有对应实现与演示路径，无「规划中但声称完成」项 |

| 可交付 | `mvn clean package` 产出可执行 jar；配置外置、日志脱敏、发布 / 回滚步骤成文 |
