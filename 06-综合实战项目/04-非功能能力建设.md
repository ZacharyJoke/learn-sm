# 04 · 非功能能力建设

> 功能正确只解决「能用」，非功能能力决定「敢不敢上生产」。本篇覆盖性能、日志脱敏、异常体系、安全加固与可观测性，措施均以真实工程为基线。

## 1. 性能

### 1.1 JMH 基准（占位，发布前实测回填）

| 基准方法（建议） | 模式 | 单位 | 实测值 | 说明 |
|------------------|------|------|--------|------|
| `Sm3Benchmark.digest_1KB` | AverageTime | us/op | 待实测 | 1 KB 报文 SM3 摘要 |
| `Sm3Benchmark.digest_1MB` | AverageTime | ms/op | 待实测 | 流式摘要对照 |
| `Sm4Benchmark.gcmThroughput_1MB` | Throughput | MB/s | 待实测 | GCM 加密吞吐 |
| `Sm4Benchmark.cbcThroughput_1MB` | Throughput | MB/s | 待实测 | CBC 加密吞吐 |
| `Sm2Benchmark.sign` | AverageTime | ms/op | 待实测 | 单次 SM2 签名 |
| `Sm2Benchmark.verify` | AverageTime | ms/op | 待实测 | 单次 SM2 验签 |
| `EnvelopeBenchmark.seal_4KB` | AverageTime | ms/op | 待实测 | 含一次 SM2 + GCM |
| `EnvelopeBenchmark.open_4KB` | AverageTime | ms/op | 待实测 | 含一次 SM2 + GCM |

基准纪律：固定 JDK 与 BC 版本；fork 1、warmup 与 measurement 各 5 轮；报告中位数与 P99；数值进仓库随版本演进，禁止凭印象写性能结论。

### 1.2 优化原则（已体现在架构中）

**SM2 少调用 —— SM2 是最贵的运算：**

- 信封中 SM2 只加密 16 字节 DEK，绝不直接加密业务正文，成本与正文长度脱钩；
- 单次 HTTP 签名请求在拦截器内只做一次验签，业务链路中不得重复验签；
- 公钥目录解析为内存 Map 查找，密钥本身不重复反序列化；未来可对 `KeyFactory` 结果做缓存（DER 字节 → PublicKey）。

**SM4 批量与分块：**

- 大报文走 `update` 分块 + 一次 `doFinal`，避免「每块一次 doFinal」的重复初始化与标签开销（GCM 一个流式实例只产出一个 tag）；
- 批处理场景合并小报文为批次，DEK 与会话按批次建立一次；
- GCM nonce 固定 12 字节，避免更长 nonce 触发的内部 GHASH 预处理成本。

**会话复用：**

- HTTP 层开启 keep-alive 长连接，复用 TCP / TLS 握手；
- 与对端约定会话密钥：会话建立时一次 SM2 协商 / 分发会话 SM4 密钥，会话内对称保护，避免「每消息一次 SM2」；
- 可复用的重对象仅限线程安全者：`KeyPairGenerator`、`SecureRandom` 可单例复用；`Cipher` / `Signature` 严禁共享（见 03 篇线程安全）。

## 2. 日志脱敏

### 2.1 脱敏红线

任何日志都不得出现：明文、对称密钥、私钥、可被直接重放的完整签名报文；密文默认不落 INFO。允许出现：keyId、算法、操作、结果、字节长度、短指纹（如 SM3 前 8 位）。

### 2.2 ❌ / ✅ 对照

❌ 直接打印密钥：

```java
log.info("SM4 encrypt key={}", Codec.toHex(key));
```

✅ 打印标识与指纹：

```java
log.info("SM4 encrypt done, keyId={}, keyFingerprint={}, bytes={}",
        keyId, Codec.toHex(Sm3Support.digest(key)).substring(0, 8), plaintext.length);
```

❌ 打印明文与私钥 PEM：

```java
log.info("decrypted plaintext={}, privateKey={}", new String(plaintext), privateKeyPem);
```

✅ 打印长度与摘要指纹：

```java
log.info("decrypt success, bytes={}, digest8={}",
        plaintext.length, Codec.toHex(Sm3Support.digest(plaintext)).substring(0, 8));
```

❌ 异常链原样外抛（可能带出底层 provider 细节）：

```java
log.error("decrypt failed", rawException); // 面向访问端输出
```

✅ 边界翻译后只记错误码，详情仅留在受控的服务端 ERROR 日志：

```java
throw new GmCryptoException(ErrorCode.DECRYPTION_FAILED, "解密失败", cause);
```

### 2.3 建议的统一工具（规划）

收敛为 `LogMasking` 工具：`keyFingerprint(key)`、`digest8(data)`、`mask(String)`，让「脱敏」成为默认路径而非自觉行为，从根本上防止新人直接 `toString` 密钥。

## 3. 异常体系

### 3.1 结构

- `GmCryptoException extends RuntimeException`：持有 `ErrorCode errorCode`，提供「错误码 + 消息」与「错误码 + 消息 + 原因」两个构造器；
- 各算法工具类在 JCA 边界把 `GeneralSecurityException` / `IOException` 翻译为统一异常；
- `GlobalExceptionHandler`（`@RestControllerAdvice`）统一收口。

### 3.2 错误码表

| 错误码 | 含义 | 对外 HTTP 映射 | 备注 |
|--------|------|----------------|------|
| ALGORITHM_UNAVAILABLE | 算法 / Provider 不可用 | 500 | 环境级故障，触发运维告警 |
| INVALID_KEY | 密钥长度或格式非法 | 500 | 不回显具体密钥内容 |
| INVALID_PARAMETER | 入参非法（含未知 appId） | 400 | 处理器显式映射 |
| SIGNATURE_INVALID | 签名 / 验签操作异常 | 500 | 验签「结果为 false」由拦截器直接 401 |
| ENCRYPTION_FAILED | 加密失败 | 500 | — |
| DECRYPTION_FAILED | 解密 / GCM 完整性失败 | 500 | 不区分「密钥错」还是「被篡改」，避免预言机 |
| INTEGRITY_CHECK_FAILED | 信封摘要复核失败 | 500 | `open` 业务层校验 |
| REQUEST_EXPIRED | 请求时间戳过期 | 预留 | 现由拦截器直接 400 拒绝 |
| REPLAY_DETECTED | nonce 重放命中 | 预留 | 现由拦截器直接 409 拒绝 |
| KEY_NOT_FOUND | 密钥版本不存在 | 400 | 处理器显式映射 |
| AUDIT_FAILED | 审计执行失败 | 500 | 预留，供审计接入流水线时使用 |

### 3.3 不泄密原则

`GlobalExceptionHandler` 真实映射逻辑：

```java
HttpStatus status = switch (exception.getErrorCode()) {
    case KEY_NOT_FOUND, INVALID_PARAMETER -> HttpStatus.BAD_REQUEST;
    default -> HttpStatus.INTERNAL_SERVER_ERROR;
};
return ResponseEntity.status(status).body(Map.of(
        "errorCode", exception.getErrorCode().name()));
```

- 响应体只有 `errorCode`，没有内部消息、没有异常类型、没有堆栈：调用方足以分支处理，攻击者拿不到额外信息；
- 解密失败与篡改失败统一为 `DECRYPTION_FAILED`，不提供「哪一段错了」的反馈，消除错误预言机；
- 拦截器的拒绝消息（缺头 / 过期 / 错签 / 重放）属于协议级提示，不涉及任何密钥与明文。

## 4. 安全加固

### 4.1 密钥来源矩阵

| 密钥 / 秘密 | 本期来源 | 生产目标来源 |
|-------------|----------|--------------|
| SM4 DEK | `Sm4Support.generateKey()`（强随机，每封一次性） | 同上，或 KMS 数据密钥（GenerateDataKey） |
| GCM nonce / CBC IV | `RandomUtils.randomBytes()`，每次随机 | 同左，禁止计数器被重置 |
| SM2 收件人密钥对 | 启动时 `register("SM2")` 现场生成 | KMS / HSM 内生成，私钥不可导出 |
| 应用签名公钥目录 | `AppKeyResolver` 内存注册 | 对接应用注册中心 / 证书体系 |
| 任何真实密钥 | **禁止**进入 yml / 代码 / 日志 | 环境变量引用 keyId，素材由托管系统持有 |

### 4.2 AAD 绑定 keyId 的防御含义

GCM 的 AAD 是「经认证但不加密」的上下文。信封把 `recipientKeyId` 作为 AAD：

- 正常路径：收件人用自己的私钥解开 DEK，再以自身 keyId 为 AAD 通过 tag 校验；
- 攻击路径：攻击者截获信封后把 `recipientKeyId` 改为受害者 B 的 keyId（试图让 B 解密并处理），由于 AAD 与加密时不一致，GCM tag 校验立即失败；
- 这把「密文 + 密钥 + 身份」焊成一个整体，是跨密钥上下文重放的结构性防线。

### 4.3 其他安全控制

- 默认安全算法选择：认证加密 GCM 优先；ECB 被审计规则 `GM-ECB` 视为 HIGH 反模式，业务代码不得封装；
- 时间戳 ±300 秒窗口 + nonce 一次性（TTL = 2 倍窗口）+ 先验签后登记，构成完整防重放闭环；
- 依赖供给链：BC 版本在 `pom.xml` 单点锁定为 1.84，升级需跑全量标准向量；建议开启依赖校验（checksum / 私服代理）；
- 演示数据无敏感信息；测试中的固定十六进制值是**公开标准向量**，不构成真实密钥泄露。

### 4.4 当前安全边界（须知）

`LocalKeyVersionStore` 为内存实现：私钥在进程内存中、重启即失，不满足生产密钥托管要求。上线前必须以 KMS/HSM 实现替换 `KeyVersionStore`，接口契约已为此预留。

## 5. 可观测性

### 5.1 运行时指标规划（Micrometer 命名）

| 指标名 | 类型 | 标签 | 含义 | 本期状态 |
|--------|------|------|------|----------|
| `gm.crypto.operation.total` | Counter | algorithm, operation, result | 密码操作次数与成败 | 规划（现以 INFO 日志体现） |
| `gm.crypto.operation.duration` | Timer | algorithm, operation | 操作延迟分布 | 规划 |
| `gm.sign.verify.total` | Counter | result | 验签通过 / 失败计数 | 规划 |
| `gm.replay.detected.total` | Counter | — | 重放拦截计数 | 规划 |
| `gm.nonce.store.size` | Gauge | — | 当前 nonce 表规模（容量治理） | 规划 |
| `gm.audit.findings.total` | Counter | ruleId, severity | 审计命中计数 | 本地 CLI 已输出告警 |
| `gm.key.status` | Gauge | keyId, algorithm, status | 密钥版本状态 | 规划 |

落地建议：依赖 `spring-boot-starter-actuator` + Prometheus registry；标签基数可控（禁止把 nonce、digest 当标签）；失败类指标接告警阈值。

### 5.2 审计埋点（已实现）

- `CryptoAuditor`：5 条规则静态扫描，结论为 `AuditFinding(ruleId, severity, path, line, message)`；
- `AuditCliRunner`：`--audit=<path>` 触发，以 WARN 输出 `规则号 文件:行号 说明`，可直接重定向到质量门禁；
- 建议把审计接入 CI 的「编译后、打包前」阶段，HIGH 命中即失败。

### 5.3 结构化日志字段约定

关键操作日志建议统一字段：`timestamp`、`app`、`operation`、`algorithm`、`keyId`、`result`、`bytes`、`traceId`。密钥与明文永不入日志，`traceId` 串联「验签 → 信封 → 业务处理」全链路，出问题时可在不接触秘密的前提下完成定位。
