## 2. 做得好的 5 点

1. **安全默认，而不是安全提醒**
   默认 GCM、nonce/IV 每次强随机、tag 128 位、密钥零硬编码。使用方沿默认路径走就是安全的，反模式（ECB/弱随机/固定 IV）反而需要额外努力才能引入，并会被审计器抓到。

2. **标准向量前置为自动化断言**
   不相信「人眼看一遍没问题」。SM3 与 SM4 的国家标准向量直接写进 JUnit 断言，任何 BC 升级或环境漂移导致的算法偏差会立刻红灯，这是互信互通的底线。

3. **分层清晰、依赖单向**
   `codec/random` → 算法层 → `envelope` 组合 → `key`/`web` 接入，环头只能引用下层。单模块内依然保持包级边界，后续抽取公共库时可以按包平移。

4. **线程安全纪律统一**
   有状态的 JCA 对象（`Cipher`/`Signature`/`Mac`/`MessageDigest`）方法内新建、用完即弃；共享的只允许线程安全对象（`SecureRandom`/`HexFormat`/`ObjectMapper`）与并发容器。规则简单，所以能被一致执行。

5. **安全左移：审计器进工程**
   把资深评审脑子里的检查项（内嵌私钥、全零 IV、硬编码 Hex）沉淀为 5 条正则规则与命令行入口，让机器做重复检查，人只看结论。

## 3. 踩坑与改进

### 3.1 BouncyCastle 版本锁定

坑：JCE 生态中 BC 极易因传递依赖出现多版本共存（jdk15on / jdk18on 并存），表现为「本地能跑、CI 或他机偶发 `NoSuchAlgorithmException`」。

改进：

- `pom.xml` 单点声明 `bc.version=1.84`，统一使用 `bcprov-jdk18on`；
- 取实例显式传入 `new BouncyCastleProvider()`，不依赖全局注册顺序；
- 升级 BC 必须重跑标准向量与全量 23 用例，作为硬性流程写入规范。

### 3.2 SM2 用户 ID 必须在 init 前 setParameter

坑：SM2 的 userId 参与 Z 值与摘要预处理。若先 `initSign` 再 `setParameter`，或签名 / 验签双方 userId 不一致，表现为验签恒 false，且报错信息不直观。

真实调用顺序：

```java
Signature signature = Signature.getInstance("SM3withSM2", new BouncyCastleProvider());
signature.setParameter(new SM2ParameterSpec(userId)); // 必须先设置
signature.initSign(privateKey);                       // 再初始化
signature.update(message);
```

改进：默认使用国密标准 userId `1234567812345678`；用 `mismatchedUserIdRejected` 用例把「userId 是签名上下文的一部分」固化为回归保护；封装层固定顺序，业务侧无法绕过。

### 3.3 MockMvc header 的追加语义

坑：`MockHttpServletRequestBuilder.header(name, value)` 对同一 header 名**多次调用是追加多值，不是覆盖**。测试里若先 `.header(X-Signature, wrong)` 再补一个正确签名，请求会携带两个同名头，行为与预期不符，排查时容易误判为拦截器缺陷。

改进：

- 需要「覆写」签名时，不做二次 `.header`，而是在构建 builder 前通过参数决定最终值（本工程 `signedRequest(..., signatureOverride)` 的写法）；
- 整体设置使用 `.headers(HttpHeaders)`，替换心智取代追加心智；
- 断言多值场景时明确使用 `getHeaders(name)` 语义。

### 3.4 nonce 的次序与生命周期

坑：若先登记 nonce 再验签，攻击者可不持有合法密钥、仅靠随机 nonce 灌爆 nonce 表；nonce 若不清理则长期运行内存增长；TTL 与时间戳窗口不一致会出现「重放判定」灰色地带。

改进：

- 严格「先验签通过 → 后 `registerIfAbsent`」，非法请求不落表；
- 写入前 `prune` 清理过期项；nonce TTL 取时间窗口的 2 倍（默认 600 秒），与过期边界对齐；
- 生产环境把 `NonceStore` 替换为 Redis 等带原生 TTL 的共享存储，支持多实例。

### 3.5 测试密钥管理

坑：为了「测试可复现」很容易把固定私钥 / 固定对称密钥提交进仓库，进而被复制到生产配置；公开测试向量与真实密钥的界限也常被混淆。

改进：

- 测试密钥一律在 `@BeforeEach` / 用例内动态生成（`generateKeyPair()`/`generateKey()`），仓库中不存在任何可用私钥；
- 唯一固定的十六进制值是**公开发布的标准算法向量**（SM4-ECB key 与明文同值的那组），且仅用于正确性验证，出现在 test 目录；
- Web 测试中 appId 公钥动态注册，用例之间互不依赖。

## 4. 复用规划

### 4.1 沉淀为 crypto-common

- 将 `codec`、`random`、`sm3`、`sm4`、`sm2` 五个无 Spring 依赖的包抽成独立基础库（纯 JDK + BC），供所有业务以 Maven 坐标引入；
- `envelope` 作为可选高级模块；Spring 自动装配（starter 化）在上层封装；
- 基础库只保留静态无状态 API，保证易测、易 shaded、易升级。

### 4.2 对接 KMS / HSM

- 以 `KeyVersionStore` 为切入点实现 KMS 版本：注册走 `CreateKey`，信封 DEK 优先用 `GenerateDataKey`（返回明文 + 密文双份），私钥永不落地；
- HSM 场景通过 JCA/JCE 或 PKCS#11 通道在硬件内完成 SM2 签名，应用只拿到签名值；
- 密钥轮换、吊销、审计日志交由托管系统，本工程保留版本元数据模型与之映射。

### 4.3 上收到 API 网关

- 把「四头验签 + 时间戳 + nonce」从应用拦截器演进为网关 / 服务网格统一插件，业务服务只信任网关透传的认证结果头；
- 网关维护 appId 公钥目录与分布式 nonce，密钥管理集中化；
- 应用内拦截器作为内网纵深防御保留，形成「网关 + 应用」双层校验。

## 6. 结语

`gm-crypto-suite` 的价值不在「实现了三个算法」，而在演示了一条可复制的路径：**以标准向量保证正确性、以安全默认降低出错面、以分层抽象为基础设施演进留口、以审计与测试把经验固化进流水线**。

下一步把无状态算法层抽成 `crypto-common`，把密钥与防重放交给 KMS 与网关，本工程即从「教学参照」平滑长成「生产骨架」。
